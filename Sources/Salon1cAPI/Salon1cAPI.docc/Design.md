# Design

Every load-bearing decision in `Salon1cAPI`, with the alternative that was rejected.

## Generated, not handwritten

All 53 operations are generated by Apple's swift-openapi-generator from
`Sources/Salon1cAPI/openapi.yaml`. The handwritten layer is thin on purpose:

- ``Credentials`` — the two header credentials.
- `AuthMiddleware` — injects `apikey` always and `usertoken` when present.
- `Client+init` — convenience initializers that compose the transport and middleware.

**Rejected:** a hand-written client. The document already knows every path, parameter,
and body; duplicating that knowledge in Swift guarantees drift. Handwritten surface area
exists only where the document cannot express intent — header injection and construction
ergonomics.

## The specification is owned, not vendored

`openapi.yaml` is authored by this repository and its `Upstream/salon1c/salon1c.apib`
snapshot is provenance, not source of truth. That is a deliberate inversion of the
usual "vendor ships the spec" arrangement — see <doc:SpecOwnership> for what it
obligates. Practically it means: **spec problems get fixed in `openapi.yaml`, never
worked around in Swift.** A handwritten extension that papers over a generated shape is
a workaround with a fixable root cause.

## Fidelity over normalization

The API's document contradicts itself — envelope capitalization differs per group,
`phone` is `number` in one operation and `string` in the next, `amount` is declared
`number` but sent as a quoted string in the v2 example, examples contain typos
(`rsating`, `avialable_actions`, `visites`).

The spec models what each operation **declares**, preserves the wire spellings
(`avialable_actions` stays), and registers each conflict in <doc:TechDebt> rather than
"correcting" toward symmetry. Rationale: this API predates OpenAPI discipline; its
actual wire behaviour — which the document sometimes misdescribes — can only be
verified by the live suite (TD-1). Normalizing first would guess which side of each
conflict is real. **Replicate documented behaviour; change it only on evidence.**

## Envelopes are the contract, not an obstacle

Every operation returns its documented envelope — `{parameters, errors}` and its six
variants. There is no `client.getSalons() -> [Salon]` that silently unwraps
`Parameters` and swallows `errors`. Rationale:

- Domain errors arrive with HTTP 200 inside `errors.code`. An unwrapping layer must
  decide what a non-zero code means — throw? return nil? — and that decision is the
  app's business, not the client's. Two error channels stay distinct on purpose:
  documented non-2xx statuses are `Output` enum cases you `switch` on; transport and
  decoding failures are thrown `ClientError`s.
- The envelope *varies* — `Meta` vs `Pagination` vs `navigation`, `Errors` vs `Error`
  vs `errors`-inside-`parameters`. Any facade must answer "which shape?" per operation,
  re-encoding the document's knowledge in Swift. The generated code already encodes it
  correctly.

Unwrapping helpers are planned as an opt-in layer (<doc:Roadmap>), not a replacement.

## `operationId` names operations, not `nameOverrides`

Operation method names come from `operationId` (`getCartCost`, `authorizeTerminal`).
`nameOverrides` is not used for operations: one override string is returned verbatim
for both the method name and its `Operations.*` namespace, which cannot produce
idiomatic Swift for both. Verified upstream; see the sibling package's write-up in
`../YooMoneyAPIClient/Upstream/nameoverrides-verbatim-casing.md`.

## JSON-in-query is modeled, not stringly-typed

The API describes parameters like `cart` as «строка Json» — a JSON document inside a
query value. The spec declares them `in: query` with `content: application/json`, so
the generator emits `setQueryItemAsJSON` and callers pass typed values
(`[CartQueryItem]`, `ServiceIdsQuery`). **Rejected:** `type: string` + a hand-serializer
— that pushes JSON knowledge into every call site and loses validation.

This required OpenAPI Runtime ≥ 1.13; `setQueryItemAsJSON` first shipped there and the
pin is load-bearing.

## `SalonId` is a path parameter, not client state

Every v1 path carries `{salon_id}` — including operations whose bodies *also* carry
`salon_id` (the clients group duplicates it). The client takes it per-call rather than
at construction, because a multi-salon deployment (the document's own examples switch
salon ids between examples) is a legitimate caller. `Credentials` holds only what rides
in headers.

## Security declaration follows the document

`apikey` is the package's global security scheme; `usertoken` is declared per-operation
exactly where the document shows the header — including the odd cases: `cart_cost`
*advertises* `usertoken` but returns a `user_token` in the response when it's absent
(a token-vending mechanism), and `deposit_detail` shows only `apikey`. `AuthMiddleware`
injects `usertoken` on every request when credentials carry one — sending an extra
documented header is harmless; failing to send a required one is not.

## Platform floor and isolation

iOS 17 / macOS 14 / tvOS 17 / watchOS 10 / visionOS 1 — no `@available` anywhere; the
generator's concurrency requirements already meet this floor. The package builds with
`.defaultIsolation(nil)`: generated `Codable` types are `Sendable` value types, and
forcing an actor domain onto them buys nothing.
